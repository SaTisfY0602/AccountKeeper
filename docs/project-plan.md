# AccountKeeper 项目规划

## 产品定位

AccountKeeper 的长期目标不是单纯的账单导入器，而是一个本地优先的自动省钱管家。

它应该逐步做到：

- 自动识别微信、支付宝、银行卡等来源的收入和支出。
- 自动判断交易平台、实际扣款账户、商户、分类和交易方向。
- 自动发现重复记录，尤其是“微信/支付宝支付 + 银行卡扣款”的双记录场景。
- 根据月度预算或年度攒钱目标，动态计算每日推荐额度。
- 在首页显示今日还能花多少、累计结余多少、是否超额。
- 当支出超出计划或疑似不合理时，提醒用户及时调整。

当前阶段先保证本地账本可用，后续围绕自动识别、预算控制和省钱建议逐步升级。

## 目标设备与兼容策略

- 主目标设备：vivo X200 Pro。
- 主目标系统：OriginOS 6。
- OriginOS 6 基于 Android 16，因此项目需要适配 API 36。
- 当前 Android 配置：
  - `compileSdk 36`
  - `targetSdk 36`
  - `minSdk 23`
- 保持 Android 6.0 及以上兼容，除非某个关键能力确实要求更高版本。
- 继续保持 core library desugaring，以便旧系统也能使用 `java.time` 等 API。

## 当前实现

当前 App 已实现一个轻量 MVP：

- 手动记账。
- 账户管理。
- 流水列表。
- CSV 粘贴导入。
- 首页收支统计。
- 简单疑似重复检测。

当前代码结构：

- `MainActivity.kt`：启动入口。
- `AccountKeeperApp.kt`：Compose 界面。
- `LedgerModels.kt`：账本数据模型。
- `LedgerStore.kt`：本地 JSON 存储。
- `DuplicateMatcher.kt`：重复识别逻辑。
- `LedgerFormat.kt`：金额、时间、CSV 示例等工具。
- `RecognitionModels.kt`：原始事件和自动识别候选模型。
- `RecognitionEngine.kt`：自动识别基础规则。
- `BudgetModels.kt`：预算计划和每日预算状态。
- `BudgetEngine.kt`：预算额度、结余滚入和超额计算。

技术栈和版本号统一记录在 `tech.md`，后续每次升级依赖或引入新技术都必须同步更新。

## 已识别的缺陷

当前实现适合验证想法，但还不适合承接复杂自动化能力。

主要不足：

- 数据仍保存在 SharedPreferences + JSON 中，不适合大量账单、查询、迁移和对账。
- 没有区分原始事件、解析结果和正式账本，后续自动识别容易污染正式数据。
- CSV 解析非常简化，不能稳定处理真实微信、支付宝、银行账单格式。
- 重复识别规则过粗，只按金额、平台和时间判断，容易漏判或误判。
- 分类体系写死在代码里，不支持二级分类、商户规则和用户习惯学习。
- 没有预算模型，无法计算每日推荐额度、结余滚入和超额提醒。
- 没有待确认队列，自动识别结果无法被用户集中审核。
- 没有通知监听、短信识别、分享入口、OCR 等自动数据来源。
- UI 还只是基础可用状态，未针对长期记账和省钱管理做高频操作优化。

## 修正后的总体架构

后续应把系统拆成五层：

1. 数据来源层

   负责接收外部信息，不直接写入正式账本。

   可能来源：

   - 通知监听：微信、支付宝、银行 App 的消费和到账通知。
   - 短信识别：银行消费、入账、信用卡还款等短信。
   - 账单导入：微信、支付宝、银行卡导出的 CSV/Excel。
   - 分享入口：从支付详情页或账单页分享文本到 App。
   - OCR：识别截图里的金额、商户、时间和账户。
   - 手动记账：作为兜底入口。

2. 原始事件层

   所有来源先进入 `RawEvent`。

   `RawEvent` 应保留：

   - 来源类型。
   - 原始文本或文件片段。
   - 捕获时间。
   - 来源 App 或账单文件名。
   - 处理状态。
   - 隐私敏感字段标记。

3. 解析识别层

   把 `RawEvent` 转成 `ParsedTransaction`。

   识别内容包括：

   - 收入或支出。
   - 金额。
   - 发生时间。
   - 交易平台。
   - 实际账户。
   - 商户或交易对象。
   - 分类候选。
   - 置信度。
   - 解析规则版本。

4. 账本确认层

   `ParsedTransaction` 不应直接变成正式账本。

   应先进入待确认队列：

   - 高置信记录可以自动入账，但仍保留撤销入口。
   - 中置信记录默认等待用户确认。
   - 低置信记录只提示，不自动计入统计。

   正式账本使用 `LedgerTransaction`，只统计确认后的交易。

5. 预算与提醒层

   预算系统独立于导入系统。

   它读取正式账本，计算：

   - 月度预算。
   - 年度攒钱目标。
   - 今日推荐额度。
   - 今日已花。
   - 未花完结余。
   - 未来每日剩余额度。
   - 超额风险。

## 自动识别策略

推荐路线：

1. 通知监听作为主方案。
2. 短信识别补银行卡。
3. 账单导入用于月底校准和补漏。
4. 分享入口用于用户主动补单。
5. OCR 作为后期能力。
6. 无障碍服务只作为高级模式，不作为默认主方案。

原因：

- 通知监听最适合实时更新今日额度。
- 短信对银行和信用卡仍然有价值。
- 导入账单适合补齐历史和检查漏记。
- 分享和 OCR 能补通知没覆盖的场景。
- 无障碍服务能力强，但权限敏感、稳定性受系统影响大，尤其要考虑 OriginOS 后台管理。

## 去重策略

去重不能只按金额判断，必须有置信度。

建议等级：

- 高置信：金额相同、时间接近、商户相似、平台链路一致，例如微信支付和银行卡财付通扣款。
- 中置信：金额相同、时间接近，但商户不明确。
- 低置信：只有金额接近或描述相似。

处理规则：

- 高置信可以建议自动合并。
- 中置信进入待确认队列。
- 低置信只在对账页展示。
- 所有合并都保留原始记录，方便回溯。

## 分类策略

分类需要从写死列表升级为规则系统。

应支持：

- 一级分类：餐饮、交通、购物、居住、医疗、娱乐、学习、收入、转账等。
- 二级分类：早餐、外卖、打车、房租、数码、药品、工资等。
- 商户关键词规则。
- 平台规则。
- 用户修正规则。
- 置信度。

用户每次修改分类，都可以生成一条个人规则。比如用户把“瑞幸咖啡”改成餐饮后，下次自动识别为餐饮。

## 预算和省钱管理

预算系统是后续核心功能。

基础规则：

- 用户可以设置月度消费目标，例如每月最多花 2000 元。
- 用户也可以设置年度攒钱目标。
- App 根据剩余预算和剩余天数生成每日推荐额度。
- 当某天未花完，剩余额度自动滚入后续天数。
- 当某天超额，后续每日推荐额度自动降低。
- 首页显示今日可用额度、今日已花、本月剩余、本月进度。

示例：

- 月预算：2000 元。
- 本月已花：600 元。
- 本月剩余：1400 元。
- 剩余天数：20 天。
- 今日推荐额度：70 元。

如果今天只花 40 元，剩余 30 元进入后续预算池。

如果今天花 100 元，App 提醒今日超出 30 元，并重新计算后续每日额度。

## 提醒策略

提醒不应太吵。

建议分级：

- 轻提醒：今日花费达到推荐额度 80%。
- 明确提醒：今日花费超过推荐额度。
- 风险提醒：连续多日超额，可能影响月目标。
- 异常提醒：短时间内多笔同类消费，或金额明显偏高。

提醒内容应尽量具体：

- 不是只说“你超额了”。
- 而是告诉用户“今日推荐 70 元，已花 100 元，超出 30 元；本月剩余额度将降为每天约 68 元”。

## 推荐实施顺序

第一阶段：数据底座

- 从 JSON 迁移到 Room。
- 增加 `RawEvent`、`ParsedTransaction`、`LedgerTransaction` 三层模型。
- 增加待确认队列。

第二阶段：预算系统

- 增加月预算。
- 增加今日推荐额度。
- 增加结余滚入。
- 首页展示预算状态。

第三阶段：自动识别 MVP

- 增加通知读取权限。
- 解析微信、支付宝、银行通知。
- 自动生成待确认交易。

第四阶段：自动分类和自动去重

- 增加规则引擎。
- 增加分类置信度。
- 增加重复候选队列。
- 支持用户修正规则。

第五阶段：对账和补漏

- 支持微信、支付宝、银行卡账单文件导入。
- 支持月底对账。
- 支持批量确认和批量合并。

第六阶段：省钱建议

- 增加消费合理性判断。
- 增加分类预算。
- 增加年度攒钱目标。
- 增加趋势分析和风险提醒。

## 暂不做的事项

为避免早期复杂度失控，暂不优先做：

- 云同步。
- 多用户账户。
- 投资资产管理。
- 复杂 AI 大模型分类。
- 默认启用无障碍读屏。
- 直接读取微信、支付宝或银行 App 的内部数据。

这些能力以后可以评估，但不应阻塞当前主线。

## 设计原则

- 本地优先，账单数据默认只存在用户手机里。
- 自动识别结果必须可解释、可撤销、可追溯。
- 任何自动合并和自动分类都应保留置信度。
- 预算提醒要帮助用户省钱，而不是制造焦虑。
- 兼容 vivo X200 Pro / OriginOS 6，同时尽量保持更广泛 Android 版本支持。
- 后续新增功能优先接入统一管线，不为某个来源写孤立逻辑。
